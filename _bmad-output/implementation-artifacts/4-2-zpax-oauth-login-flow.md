# Story 4.2: z-pax OAuth Login Flow

Status: review

## Story

As a visitor or existing user,
I want to sign in via z-pax SSO,
so that I can access my account without creating a separate password.

## Acceptance Criteria

1. **Given** the Login page, **when** a user clicks "Sign in with z-pax", **then** the backend generates a random `state` value, stores it in a short-lived cookie, and redirects the browser to z-pax's authorization endpoint (`https://sapi.auth.myzpax.com/connect/authorize`) with `client_id`, `scope=api`, `response_type=code`, `redirect_uri`, `fallback_uri`, and `state` (AD-19, FR42). **Updated 2026-08-24** against z-pax's real `/connect/authorize` API reference: `scope=api` replaces this AC's original `offline_access profile` guess (z-pax's doc lists `scope`'s value the same single-word way it lists `response_type=code` — a literal required value, not free-form OAuth scopes) and `fallback_uri` (required per that same reference, undocumented purpose) is now sent, set to the same `https://localhost:5173/login?error=sso_failed` target as this story's own failure redirect (Task 4) as a reasonable default for "no real z-pax credentials to trial against yet." **Pending live verification once real z-pax credentials are available** — confirm `scope=api` alone still grants `/connect/userinfo` access, and observe what z-pax actually does with `fallback_uri` in practice.
2. **Given** a successful authorization, **when** z-pax redirects back to `/api/auth/sso/callback` with a `code` and `state`, **then** the backend first validates `state` matches the stored value — rejecting the callback (redirect to Login with an error, no account created or session issued) on a missing or mismatched `state` — then exchanges `code` at `https://sapi.auth.myzpax.com/connect/token` for a z-pax access token, calls `GET https://sapi.auth.myzpax.com/connect/userinfo` with that access token to fetch the user's `id`/`email`/`firstName`/`lastName`, and resolves the local account via `CreateOrLinkSsoAccount` from Story 4.1 (FR43, FR44, AD-19).
3. **Given** the resolved account, **when** the SSO flow completes, **then** the app mints its own access token (in-memory) and refresh token (HttpOnly cookie) exactly as `POST /api/auth/login` does, and routes the user per FR4 (AD-3, AD-19).
4. **Given** automated tests should never depend on a live external service (mirrors AD-4), **when** this story is implemented, **then** the OAuth calls are built against an injected `ISsoClient` abstraction with a fake test double for xUnit coverage, while the real `ISsoClient` implementation targets z-pax's actual endpoints (AD-19) using the real Client ID/Secret expected to be available by implementation time.
5. **Given** z-pax returns an error or the callback is missing/invalid `code`, **when** this happens, **then** the user is redirected to Login with an on-screen error, and no account is created or session issued.

### Design Decisions This Story Must Make (epics/architecture leave these open)

- **`ssoState` cookie must be `SameSite=Lax`, never `Strict`.** See Task 4 — this is the single highest-risk, easiest-to-get-silently-wrong detail in this story, because `refreshToken`'s existing `SameSite=Strict` is the pattern immediately at hand to copy, and copying it here would make `state` validation fail on every real browser flow while every automated test (which never performs a true cross-site top-level navigation) would still pass. Structural cause: `Strict` cookies are withheld by the browser on cross-site top-level navigations (z-pax → our callback); `Lax` cookies are still sent on that specific navigation type (top-level GET).
- **The frontend redirect target is hardcoded, not newly configurable.** `https://localhost:5173` is already hardcoded in `Program.cs`'s CORS policy and mirrored in the fixed `redirect_uri` AD-19 itself specifies — adding a third, independent config surface for the same fixed local value would be inconsistent, not more flexible (NFR7 rules out ever needing a second value).
- **`CreateOrLinkSsoAccount` alone is sufficient per callback — do not also call `FindBySsoIdentity`.** See Task 3's explicit note; verified by reading the current `AccountRepository.cs`, this overrides a speculative note left in Story 4.1's own Dev Notes.
- **The real z-pax identity-fetch mechanism is confirmed, not guessed:** a separate `GET /connect/userinfo` call with the token-endpoint's `access_token` as a Bearer credential (`scope=profile` required on the authorize request for this reason) — not fields embedded in the token response. See Task 2. This overrides the credentials-not-yet-available placeholder assumption an earlier draft of this story carried.
- **Token exchange must resend the same `redirect_uri`** used on the authorize request — a standard OAuth2 provider check; the architecture doesn't call this out explicitly, but omitting it is a common source of a real (not simulated) integration failure that no test using `FakeSsoClient` would ever catch.

### Testing Requirements

- xUnit.v3 + `WebApplicationFactory` (`SqliteApiFactory`), no mocked `DbContext` — same as every prior story.
- `AllowAutoRedirect = false` **and** `BaseAddress = https://localhost` are both required on the test `HttpClient` for every SSO test (see Task 5) — the default `HttpClient` behavior of transparently following 302s would make it impossible to assert on `Location`/`Set-Cookie` from the redirect responses themselves; it would also break on the `sso/login`→`sso/callback`→frontend three-hop chain (the last hop points at a non-existent `https://localhost:5173` origin from the test process's point of view); and without the `https://localhost` base, `Program.cs`'s `UseHttpsRedirection()` would intercept every request with its own redirect before any SSO logic runs at all.
- Cross-request cookie handling in tests: `HttpClient`'s default `CookieContainer` will carry the `ssoState` cookie from the `sso/login` response to a subsequent `sso/callback` call on the *same* `HttpClient` instance automatically — reuse one client across both calls within a test rather than creating two.
