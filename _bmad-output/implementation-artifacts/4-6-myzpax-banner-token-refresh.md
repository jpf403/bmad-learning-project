# Story 4.6: myzPAX Banner Token Refresh

Status: done

## Story

As an SSO-authenticated user,
I want the myzPAX banner to stay alive for as long as I'm signed in,
so that I don't lose access to the cross-app launcher just because z-pax's access token is short-lived.

## Acceptance Criteria

1. **Given** the "Sign in with z-pax" flow (Story 4.2), **when** the backend builds the z-pax authorization URL, **then** the requested scope is exactly `"openid profile offline_access"` (previously `"openid profile"`), so z-pax's token response includes a refresh token (FR49, AD-19).
2. **Given** a successful token exchange at z-pax's token endpoint, **when** the response includes a `refresh_token`, **then** it is captured (`ZPaxTokenResponse`) and, at `SsoCallback`, stored in a new `zpaxRefreshToken` cookie — HttpOnly+Secure+SameSite=Strict, scoped to `/api/auth/sso` — set alongside the existing `zpaxAccessToken` and `zpaxIdToken` cookies (FR49, AD-19).
3. **Given** a signed-in session whose z-pax access token is nearing or past its lifetime, **when** the frontend proactively calls a new `GET /api/auth/sso/zpax-refresh` endpoint (`[Authorize]`'d via this app's own session), **then** the backend reads the `zpaxRefreshToken` cookie, calls z-pax's token endpoint with `grant_type=refresh_token` and the stored refresh token, and on success returns the new z-pax access token in the response body — overwriting the `zpaxRefreshToken` cookie if z-pax returns a rotated refresh token, so the next refresh doesn't use a stale one (FR49, AD-19).
4. **Given** the frontend holds a z-pax access token in memory (Story 4.4), **when** the session is active, **then** it schedules a call to `GET /api/auth/sso/zpax-refresh` ahead of the current z-pax access-token lifetime (20 minutes today) and adopts the returned token transparently, with no visible interruption to the banner (FR49).
5. **Given** the refresh call fails, **when** this happens, **then** the outcome depends on *why* it failed — these are deliberately two different cases, not one (revised 2026-09-04 at Jack's explicit direction; this was never meant to stay deferred): **(a)** no `zpaxRefreshToken` cookie is present at all (a password-only session, or an SSO session that never obtained one) — the banner degrades to its own built-in fallback strip exactly as it does today when no token is available, no error surfaced, this app's own session is completely unaffected; **(b)** a cookie *was* present but z-pax's token endpoint actually rejected it (e.g. its lifetime has elapsed) — `GET /api/auth/sso/zpax-refresh` now forces a full sign-out of this app's own session (the same server-side revocation `POST /api/auth/logout` performs: bump `SessionVersion`, clear every auth cookie) and returns `401` so the frontend redirects to `/login`, rather than silently degrading the banner while leaving the barbershop session running (FR49).
6. **Given** automated tests should never depend on a live external service (mirrors AD-4), **when** this story is implemented, **then** `FakeSsoClient` gains the new refresh method, the endpoint's cookie-present / cookie-absent / z-pax-rejects paths are covered by xUnit + `WebApplicationFactory`, and the frontend's refresh-scheduling and degrade-on-failure logic are covered by Vitest with fake timers (NFR4, AD-4).
7. **Given** the refresh mechanism has been proven to work end-to-end with a live z-pax SSO session, **when** this story is marked done, **then** z-pax's configuration for this app has been changed to a 60-minute access-token lifetime and a 21-day refresh-token lifetime (updated from 15 days, 2026-09-04, once Jack confirmed z-pax's own current refresh-token lifetime), matching this app's own token lifetimes — this alignment happens at the end of the story, not before, so the refresh mechanism is first proven against z-pax's original short-lived configuration (FR49).
8. **Given** an SSO-authenticated user opens a new tab, reloads the page, or reopens the app after the one-time `zpax-token` pickup cookie (Story 4.4) has already been consumed — the common case for every page load after the very first one following an SSO sign-in — **when** `AuthContext` bootstraps and that one-time pickup comes back empty, **then** it falls back to calling `GET /api/auth/sso/zpax-refresh` (using the still-valid `zpaxRefreshToken` cookie from this story) before defaulting to no token, so the myzPAX banner reappears for the rest of the SSO session instead of only ever mounting in the single tab that completed the original SSO redirect — closing the Story-4.4-deferred "myzPAX banner re-fetch on a stale token" gap (`ARCHITECTURE-SPINE.md` Deferred section) now that this story has built the mechanism to do so (FR49, added mid-story at Jack's direction, 2026-09-04).

### Design Decisions This Story Must Make (epics/architecture leave these open)

- **`zpaxRefreshToken` cookie expiry (21 days, changed from 15 on 2026-09-04)** — the architecture addendum doesn't state an exact value. This story originally set it to 15 days to match the existing `zpaxIdToken`/`refreshToken` convention (a token meant to survive the whole session, not a one-time pickup); updated to 21 days mid-story once Jack confirmed z-pax's own current refresh-token lifetime is actually ~21 days, and decided to align this app's own refresh token (and `zpaxIdToken`, for the same stated convention) to the same 21-day value. If z-pax's actual refresh-token lifetime is ever shorter than the cookie's expiry, that's harmless — z-pax will simply reject an expired token at its own token endpoint (AC #5's "z-pax rejects" path handles it), the cookie's own expiry is just an upper bound.
- **Unifying "missing cookie" and "z-pax rejects" into the same 404 at the API boundary** — AC #5's *original* framing described both as producing the identical degrade behavior, and Task 4 shipped that. **Superseded by Task 13 (2026-09-04):** the two cases were split into their own AC #5(a)/(b) — missing cookie still returns `404` (silent degrade), but z-pax genuinely rejecting an existing token now returns `401` and forces a full sign-out. Left here for history; do not re-unify these without revisiting Task 13's rationale.
- **Refresh cadence: fixed `setInterval`, not derived from any token-expiry claim** — the frontend has no visibility into the z-pax access token's actual expiry timestamp (it's opaque to this app). A fixed interval safely ahead of the documented lifetime is the simplest correct mechanism. Originally 15 minutes (20-minute lifetime); **recalculated to 55 minutes (2026-09-04)** once z-pax's access-token lifetime moved to 60 minutes, same 5-minute-margin rule.
- **One-shot degrade, no retry-forever** — once a scheduled refresh fails, this story stops trying for the rest of that session (clears the interval). This matches the already-documented Deferred item in `ARCHITECTURE-SPINE.md` ("myzPAX banner re-fetch on a stale token") — this story adds one automatic retry cycle beyond Story 4.4's single bootstrap-time pickup, it does not commit to indefinite retry.
