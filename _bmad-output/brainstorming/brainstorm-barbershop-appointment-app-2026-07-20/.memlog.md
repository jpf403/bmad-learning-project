- (note) stack: .NET backend, JS/React frontend, SQLite db, hashed password auth, three roles (customer/barber/admin), pages: homepage, about, scheduling
- (technique) started How Might We
- (idea) HMW implement autotesting into the app?
- (idea) HMW have users select dates for an appointment?
- (idea) HMW make the homepage interactive and impressive?
- (idea) HMW make the three permission levels (customer/barber/admin) feel different to a reviewer, not just gated pages?
- (decision) chose to ideate against: HMW make the CI/CD pipeline part of the demo?
- (idea) show GitHub repo with frequent, small pushes as visible evidence of deployment frequency
- (insight) the autotesting HMW and the CI/CD-visibility HMW are converging — automated tests running in the pipeline is itself part of "showing DORA in action"
- (idea by coach) GitHub Actions tab left open during the walkthrough, showing green checkmarks light up live on a push
- (idea) push a live update mid-presentation and let the automated tests run in front of the reviewer
- (idea) keep the pushed change deliberately simple (e.g. a text update) so the demo ends cleanly on all-green checkmarks, not a risky live change
- (direction) moving on from CI/CD-visibility HMW to next HMW question in the batch
- (decision) digging into HMW #2 (autotesting), but reframed on substance/strategy of testing rather than how it's shown in the demo (already covered under #1)
- (idea) highest-value test targets: database CRUD, login/auth, and role-based permissions
- (idea) test case: booking a barber's already-taken time slot fails with a clear error message (double-booking prevention)
- (idea) test case: already-booked time slots are filtered out of the available options shown to users during booking
- (insight) the double-booking test case links HMW #2 (autotesting) directly to HMW #3 (date/time selection) — booking-conflict logic is a shared core feature
- (direction) moving to HMW #3: how might we have users select dates for an appointment?
- (idea) Option A: free-text date/time entry, user gambles on availability — easiest to build, but ugly/impractical
- (idea) Option B: day-of-week dropdown (Mon/Tue/etc., auto-resolving to date, capped ~1 week out) feeding a dropdown of only-available times — no guessing, moderate effort, favored as the practical middle ground
- (idea) Option C: full interactive calendar widget for date selection — best-looking, most polished, but needs a calendar library and more build effort
- (idea) hybrid of B+C: a calendar widget restricted to a 7-day window (today + next 6 days), paired with a dropdown of only-available times for the selected day
- (idea) calendar disables/darkens past dates rather than restricting the window itself; availability-per-day is left to the time dropdown, not shown on the calendar
- (question) is the 7-day booking window a real business rule for the barbershop, or just an arbitrary simplification worth dropping?
- (decision) drop the 7-day booking window restriction; calendar allows any future date, disables/darkens past dates only
- (direction) continuing to remaining HMW questions
- (direction) moving to HMW #4: how might we make the homepage interactive and impressive?
- (idea) hero section: stylized scissors graphic, brief shop info/tagline, and a prominent "Schedule an Appointment" CTA button
- (idea) add a few hoverable elements to the homepage for interactivity
- (idea) hovering the "Schedule" CTA button triggers a scissors graphic popping up/animating behind it
- (direction) moving to HMW #5: how might we make the three permission levels feel distinct to a reviewer?
- (idea) separate dashboard page for staff (not shown to customers): barbers see their own scheduled appointments, admins see all appointments across all barbers
- (idea) admin gets a "manage accounts" page to promote a customer to barber or create new barber accounts directly
- (decision) the separate staff dashboard itself is sufficient to signal role distinction; no extra badge/label needed
- (insight) user priority: validation/booking-conflict logic and role structure (separate dashboards, admin account management) matter most, alongside DORA/CI-CD visibility; homepage polish is secondary. Connection: booking-conflict validation is shared core logic underlying the scheduling UI, both staff dashboards, and the test suite -- one system, not three separate features. The live push + automated tests + green checkmarks moment (HMW #1) demonstrates DORA and autotesting simultaneously and is the strongest single demo moment in the project.
