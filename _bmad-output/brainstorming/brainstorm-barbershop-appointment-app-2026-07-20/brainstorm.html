Five Questions Hit the Table

Facilitator mode means the coach only asked questions — every idea below came from the human. These five “how might we” prompts were raised in this order before ideation began in earnest.

  1. How might we implement autotesting into the app?
  2. How might we have users select dates for an appointment?
  3. How might we make the homepage interactive and impressive?
  4. How might we make the three permission levels feel different to a reviewer, not just gated pages?
  5. How might we make the CI/CD pipeline part of the demo? Raised last, but chosen as the first one to actually dig into.
First explored

How might we make the CI/CD pipeline part of the demo?

Of the five, this is the one that got dug into first — the session picked it deliberately over the other four.

  • Show the GitHub repo with frequent, small pushes as visible evidence of deployment frequency.
  • Push a live update mid-presentation and let the automated tests run in front of the reviewer.
  • Keep the pushed change deliberately simple — e.g. a text update — so the demo ends cleanly on all-green checkmarks, not a risky live change.
Spark from the facilitator Leave the GitHub Actions tab open during the walkthrough, so green checkmarks light up live on a push.

HMW #2

How might we implement autotesting into the app?

Reframed away from the demo-visibility angle (already covered above) and onto the substance and strategy of what actually gets tested.

Highest-value test targets:

Database CRUD Login / auth Role-based permissions
FAILS Booking a barber’s already-taken time slot fails with a clear error message — double-booking prevention.
FILTERED Already-booked time slots are filtered out of the available options shown to users during booking.
Insight The double-booking test case links this question directly to date/time selection — booking-conflict logic is a shared core feature.
feeds into the date-selection question below
HMW #3

How might we have users select dates for an appointment?

The most thoroughly explored question of the five — three options weighed, merged into a hybrid, then refined by a decision.

Option A — Free text

User types a date/time and gambles on availability. Easiest to build; ugly and impractical.

Effort
Finish
Favored middle ground

Option B — Day dropdown

Day-of-week dropdown auto-resolves to a date (capped ~1 week out), feeding a dropdown of only-available times. No guessing.

Effort
Finish

Option C — Calendar widget

Full interactive calendar for date selection. Best-looking, most polished; needs a calendar library and more build effort.

Effort
Finish
Option B+Option C→ Hybrid: calendar restricted to a 7-day window, paired with a dropdown of only-available times for the selected day
Refinement The calendar disables/darkens past dates rather than restricting the window itself; per-day availability stays in the time dropdown, not shown on the calendar.
Open question Is the 7-day booking window a real business rule for the barbershop, or just an arbitrary simplification worth dropping?
✂ Decided Drop the 7-day window restriction. The calendar allows any future date; past dates are simply disabled/darkened.

HMW #5

How might we make the three permission levels feel different to a reviewer, not just gated pages?

Resolved around a separate staff dashboard with expanding scope by role.

Customer

  • Books appointments
  • Standard site pages only

Barber

  • Separate staff dashboard
  • Sees their own scheduled appointments

Admin

  • Same staff dashboard
  • Sees all appointments across all barbers
+ Manage Accounts: promote a customer to barber, or create new barber accounts directly

Extra badge or label marking each role — decided the separate staff dashboard is sufficient on its own to signal role distinction.
